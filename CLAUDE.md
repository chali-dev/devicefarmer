# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Cloud-phone management platform: a Node.js/TypeScript control plane that manages Android containers (redroid) on a Linux host and reuses DeviceFarmer STF for device management and remote control. npm workspaces monorepo: `apps/api` (Fastify), `apps/web` (Vite + Vue 3 Composition API + Ant Design Vue + Pinia + vue-i18n). The UI is bilingual (zh-CN/en); docs and many code comments are Chinese. Devices are called 设备 in the UI and `instances` in code.

## Commands

```bash
# Dev dependencies (Postgres on 5432, Redis on 6380: 6379 is taken on this machine)
docker compose -f docker-compose.dev.yml up -d
docker compose -f infra/stf/docker-compose.yml up -d --build   # STF + RethinkDB + adb server
limactl start redroid                                          # Linux VM that runs redroid (see below)

npm run dev:api          # tsx watch, reads ../../.env; http://127.0.0.1:3000, /api/health checks every dependency
npm run dev:web          # Vite on :5173, proxies /api (incl. WebSockets) to the API
npm run typecheck        # tsc (api) + vue-tsc (web); there is no linter
npm run db:migrate && npm run db:seed    # migrate also runs idempotent TS data migrations (src/db/proxy-data-migration.ts); seed ensures the built-in admin (ADMIN_USERNAME), password only on creation
ADMIN_RESET_PASSWORD=1 npm run db:seed   # deliberately reset the built-in admin password to ADMIN_PASSWORD
cd apps/api && npx drizzle-kit generate --name <name>   # after editing src/db/schema.ts; never edit old migrations
```

If the API was started without `watch` (plain `npx tsx --env-file=../../.env src/main.ts`), backend changes need a restart.

## Environment facts that are not obvious

- **redroid cannot run in Docker Desktop**: its kernel has no binder. Android runs in the Lima VM `redroid` (`infra/lima/redroid-host.yaml`, Ubuntu arm64, `binder_linux`, nftables modules). The API talks to the VM's Docker through the forwarded socket `~/.lima/redroid/sock/docker.sock` (`DOCKER_HOST` in `.env`). Sourcing `.env` in a shell therefore redirects the `docker` CLI to the VM, not to Docker Desktop.
- Device adb ports (5555–5604) are published in the VM (on the network sidecar) and forwarded by Lima to the Mac's 127.0.0.1. STF's adb container reaches them as `host.docker.internal:<port>`, which is the device serial (`ADB_DEVICE_HOST`).
- Google's emulator has **no Linux arm64 build**, so the `emulator` engine (`adapters/runtime/emulator.ts`) is code-only and untested. It needs an x86_64 host with `/dev/kvm`.
- **Android 16 does not boot on this host**: redroid 16's gralloc needs ashmem, which Linux ≥5.18 (here Ubuntu 6.8) lacks. The `redroid-16-gapps` profile carries a `blockedReason`. Details and options: `docs/06-android-upgrade-plan.md`.
- GApps images are built locally from official, signature-verified MindTheGapps: `infra/redroid-gapps/build.sh` (`ANDROID=13|16`; `verify_jar.py` for JAR-signed 13 packages, `verify_ota.py` for OTA whole-file-signed 16 packages, then `stage.py` and the Dockerfile template). Never use third-party GApps rebuilds.
- scrcpy-server (`infra/device-tools/scrcpy/`, official Genymobile release v5.0.1, SHA-256 pinned in `fetch.sh` and the README): `fetch.sh` downloads it into the gitignored `out/` (`SCRCPY_SERVER_PATH`). Rerun it on a fresh checkout; without it the 高速 source falls back to STF.
- The app_process helpers (`infra/device-tools/capture/` → `out/cpcapture.dex`, `infra/device-tools/relay/` → `out/cprelay.dex`) are built by their `build.sh` via the shared `build-dex.sh` in a throwaway JDK container from official SDK packages (`SDK_DL` dir with `platform-33-ext3_r03.zip` and `build-tools_r34-linux.zip`, sha1 from `dl.google.com/android/repository/repository2-3.xml`). No lambdas (android.jar has no LambdaMetafactory). `out/` is gitignored, so rebuild on a fresh checkout.
- **scrcpy relay (experimental, external phones)**: set `SCRCPY_RELAY_URL=wss://<public host>/scrcpy-relay` and expose only `127.0.0.1:SCRCPY_RELAY_PORT` (3010), e.g. `ngrok http 3010` in dev (the free ngrok dev domain is fixed; free plans cap monthly data; use `--region eu`: measured from this Mac the `in` region was ~80 ms worse); in production a TLS reverse proxy routes `/scrcpy-relay` to it (no ngrok). Never expose the API port, always wss. The relay connection leaves through the phone's bound proxy like any app (BitBrowser applies it below Android). Restarting the API also restarts the BitBrowser SSH tunnels; the first session after a restart may time out on `ready`.

## Architecture

The API is the only thing browsers talk to. It enforces RBAC and relays STF; STF is never exposed to end users.

- **Two layers per device, deliberately separate.** Container lifecycle is `AndroidRuntime` (`adapters/runtime/`: `DockerHost` holds shared Docker plumbing and helper containers; `DockerRuntime` base; `RedroidRuntime`/`EmulatorRuntime` only define their container spec; `runtimeFor(engine)`). Device control is `AdbAdapter` plus `StfAdapter`. `modules/instances/ops.ts` orchestrates both: create sidecar + container, start, adb connect, boot check *via adb* (engine-agnostic), `applyDeviceSettings`, wait for STF ready, claim, then enqueue preinstall apps.
- **Network sidecar per device** (`adapters/runtime/network.ts`, `modules/network/singbox.ts`): a sing-box container owns the device's netns and adb port; the Android container joins it (`NetworkMode: container:`). With a proxy, nftables redirects TCP and DNS to sing-box and the filter chain's `policy drop` is the kill switch (no direct fallback, no IPv6, no non-DNS UDP). Proxy changes rewrite config + rules and SIGHUP (no Android restart). Legacy devices without a sidecar are converted when a proxy is first bound.
- **Tracked accounts** (追踪账号, `modules/tracked`): external public profiles a user observes, separate from their own social accounts. `tracked_accounts` (private per `user_id`, admins see all with an owner filter, others get 404; unique per user+platform+normalised handle; category text, lowercase `tags text[]` with GIN index, `favorite` flag since rows are private), `tracked_account_snapshots` (followers/following/posts/views over time, source api|manual; list shows latest + delta vs. previous follower count) and `tracked_posts` (unique per account+external id; upsert keeps first_seen_at and known values). `platforms.ts` is the registry: URL/handle normalisation (youtube @handle or /channel/UC…, instagram.com/<user>, tiktok.com/@<user>; coded errors for other hosts/paths) and an optional official-API `TrackedSource` (`capabilities`, `fetchProfile`, `fetchRecentPosts`). Only YouTube has one (`youtube.ts`, Data API v3 channels/playlistItems/videos, base URL `YOUTUBE_API_BASE`, key in `settings` key `youtube`, secret-box encrypted, write-only via admin `GET/PUT /api/settings/youtube`); Instagram/TikTok are manual entry only. Never scrape. Refresh = device-less `tracked-refresh` job (`enqueueTask`, refType `tracked_account`) running `refreshTrackedAccount(id)` (scheduler-ready, no periodic scheduling yet); manual-only platforms complete as a no-op, paused/in-progress/unconfigured are refused with codes, API failures set status `error` + `last_error_code`.
- **Account analytics** (账号分析, `modules/analytics`, page `/analytics`): numbers of the operator's OWN social accounts in `social_account_stats` (unique per account + UTC `day`; counters followers/following/posts + lifetime `total_views`/`total_likes`, day activity views/likes/shares/comments, `missing` = metrics a connection's scopes don't cover, source api|manual). Per-day gains come from `lib/counter-deltas.ts` (value − previous non-null reading via `lag`; also used by the tracked-accounts dashboard gain); views/likes per day fall back to lifetime-total differences. `PlatformAdapter.fetchAccountStats` (capability `accountStats`; `service.apiAccountStats`): Instagram profile counters + insights per UTC day (`instagram_business_manage_insights`), YouTube channels.list counters + YouTube Analytics `reports` per day (`yt-analytics.readonly`, `YOUTUBE_ANALYTICS_BASE`, ~2 days delay, Pacific days), TikTok `user.info.stats` counters only. Scopes were appended; `withOptionalScope` turns a missing/denied scope into a non-fatal `analytics.scope_missing` result so older connections keep working. Task `account-stats` (device-less, 1 attempt): daily per connected account (`scheduleDailyAccountStats`, hourly from main.ts, key `account-stats:<id>:<day>`, spread by account id, expired connections skipped) or "refresh now"; failures are the task's coded error, never the account's status. REST `/api/analytics/summary?days=1..90&ownerId&platform`, `/api/analytics/accounts/:id` (series), `POST …/stats` (manual upsert), `DELETE …/stats/:day`, `POST …/refresh`; RBAC = social accounts (users own, others 404). Dashboard widget `analytics`.
- **Proxy pool** (代理 IP, `modules/proxies`, admin only): proxies in `proxies` with `kind` static|dynamic|mobile (page tabs; `?kind=` filter, `kindCounts`; device auto-assignment ignores kind) (password AES-256-GCM via `secret-box`, write-only; status + `last_check` from a check run on the API host through the proxy with `socks-proxy-agent`/`https-proxy-agent` against api.ipify.org + ipinfo.io). A device references one via `instances.proxy_id` (UNIQUE: one proxy ↔ at most one device; FK `ON DELETE RESTRICT`, delete of a bound proxy is a 409). The sidecar config is built from the pool entry at apply time (`resolveProxyConfig` decrypts). `POST /api/proxies/test` checks an unsaved config the same way (stores nothing, audit-excluded; with `id` an empty password falls back to the stored one only for the same username). Binding (`PUT /api/instances/:id/proxy {proxyId}`) is admin only; users see their devices' proxy without username/password (`publicInstance()`). Device creation takes `proxyMode: auto|pick|none`; auto picks free ok/unchecked proxies with `FOR UPDATE SKIP LOCKED` inside the insert transaction. Editing a bound proxy's endpoint/credentials re-applies it to the device (set-proxy task). Old inline `instances.proxy` values were moved into the pool by `src/db/proxy-data-migration.ts`, run by `db:migrate` around the schema migrations.
- **Device sources** (设备来源, `modules/sources`, admin only): external phones next to local containers. `device_sources` (type, name, config jsonb without secrets; restrict-deleted while devices use it) and `instances.source_id` + `external_id` (unique per source). One `SourceDriver` per type (`types.ts`: config schema, test, listPhones, optional power on/off/isOn, openAdb/closeAdb); `ops.ts` (`ext*`) and the monitor's separate 15 s loop only call the driver, so a new kind is one driver file. The driver makes the phone's adbd reachable on `EXTERNAL_ADB_BIND:<5700–5799>` (= `adb_port`), so adb/STF/remote control/apps/social code is shared unchanged. Adding (`POST /api/instances/external`) never powers on; delete only removes the device from the platform. External phones refuse the proxy pool and device settings (`instances.engine_unsupported`). **BitBrowser** (`sources/bitbrowser.ts`, `adapters/bitbrowser.ts`, `adapters/bitbrowser-tunnel.ts`): the BitBrowser client's local API (Windows/Mac; POST JSON, ≤1 req/s, serialised per address); power-on is billed until shutdown; adb = `ssh -N -L` child per phone to BitBrowser's gateway, password fetched fresh from `/phone/adb/get` and passed only via an askpass env var, renewed 30 min before the ~28 h grant expires. Never wrap 一键新机 (`profile/recover`) or fingerprint editing; locale/time zone come from the BitBrowser profile and are re-applied on every boot.
- **Profiles** (`src/profiles.ts`) map a profile id to engine, image, `gapps`, `requiresKvm`, `memEstimateMb` and optional `blockedReason`. `GET /api/profiles` reports availability. Device creation runs a host memory capacity check.
- **All device mutations go through BullMQ** via the task centre (`modules/instances/queue.ts` registers one handler per op on the `instance-ops` queue; `enqueue`/`enqueueTask` are thin wrappers over `createTask`): create, start, stop, restart, delete, install-apk, uninstall-app, apply-settings, set-proxy, import-app, push-asset (plus device-less jobs such as media-process on `task-ops`). A failure of a device-only op (`DEVICE_OPS`) must not mark the device `error`. Routes reject actions on busy statuses.
- **Platform integrations** (平台接入, `modules/platforms`): official APIs only. `PlatformAdapter` per platform (`youtube.ts` Google OAuth+PKCE / Data API v3 resumable upload, commentThreads, comments.insert; `instagram.ts` Instagram API with Instagram Login, long-lived self-refreshing token, media container → status poll → media_publish, needs a public HTTPS media URL = S3 presigned via `media-url.ts`, local storage → `platform.media_url_unavailable`, JPEG only; `tiktok.ts` Login Kit + Content Posting API with FILE_UPLOAD chunks, inbox/draft by default, direct post only with the admin option `directPost`, comments unsupported) declares `capabilities`. App credentials live in `settings` key `platform.apps` (client secret secret-box sealed, write-only; admin `GET/PUT /api/settings/platforms[/:platform]`, page `/platforms`); redirect URI `${PUBLIC_BASE_URL ?? WEB_ORIGIN}/api/platforms/<p>/callback`; all endpoints overridable via config. `platform_connections` (1:1 social account, sealed access/refresh tokens, status connected/expired/revoked/error) never leave `connections.ts` (`publicConnection`, no events); `authed()` refreshes under a row lock, hard refresh failures mark `expired`. OAuth (`oauth.ts`): random state stored hashed in Redis (10 min, GETDEL = single use) with the sealed PKCE verifier and the hash of an HttpOnly SameSite=Lax binding cookie set by `POST /api/platforms/:p/connect`; the unauthenticated `GET …/callback` requires that cookie, exchanges the code, verifies via `fetchOwnProfile`, stores, redirects to `/social?platformConnect=…&result=…&code=…` and writes its own audit entry (`platform.connect` / `platform.connect_failed`). `DELETE /api/platforms/accounts/:id/connection` revokes best-effort and deletes tokens; `POST …/check` queues task `social-account-check` (manual-only without a connection; auth failures → account logged_out). Other modules call `service.ts` (`apiPublishUnavailableReason`, `apiPublish`, `apiListComments`, `apiReplyToComment`) with account rows, never tokens. Errors `platform.*`.
- **Task centre** (任务中心, `modules/tasks/core.ts`): the single scheduler for every background job. Modules call `registerTaskHandler(type, { run(ctx), queue, concurrency, timeoutMs, maxAttempts, backoffMs, cancellable, retryable, beforeRetry, onFailure })` at import time and `createTask({ type, userId, instance, label, refType, refId, payload, runAt, idempotencyKey, ... })`. `tasks` holds scheduling state only (statuses pending/scheduled/running/success/failed/cancelled; payload/result jsonb, attempts, last `error` + `error_code`); `task_logs` gets a line per transition plus `ctx.log`. BullMQ job id = task id, data `{taskId}`; the worker reloads the row and every transition is status-guarded. Retries: exponential backoff up to max_attempts (task returns to pending between attempts); timeout fails the attempt (`task.timeout`); cancel removes pending/scheduled jobs, running tasks get `cancel_requested` + `ctx.signal` (via the event bus; device ops just finish). Manual retry = new task with `retry_of`. Idempotency key unique per (type, key) for all time. Crash safety: workers use `maxStalledCount: 0`, a redelivered job whose task is still `running` fails it as `task.interrupted` (never reruns non-idempotent work); `reconcileTasks()` at startup fails running tasks whose job is gone and re-enqueues pending/scheduled ones. Payload is visible in the UI: never put secrets in it. REST `/api/tasks` (filters, stats, detail+logs, cancel, retry; users see own tasks + tasks on granted devices, else 404); events `task.updated` / `task.log` omit payload/result. Test-only type `test.echo` is registered only with `TASKS_TEST_HANDLERS=1`.
- **Every device/task write goes through `modules/instances/repo.ts`**, which publishes on a Redis pub/sub bus (`lib/events.ts`). `/api/events` WebSocket forwards it to browsers, filtered by RBAC.
- **Monitor** (`modules/monitor/monitor.ts`, every 5 s) reconciles Docker, sidecar, adb and STF state and re-attaches dropped adb connections. STF's `ready` flag lags reality, so health is decided by adb and Docker. Google health (`modules/google/health.ts`) runs at most every 60 s for GApps profiles; proxy egress checks every 5 min.
- **Remote control**: `/api/instances/:id/session` WebSocket. First message `{type:"auth",token}`, then RBAC, then claims the device in STF. It relays JPEG frames from STF's screen WebSocket (`display.url`, whose **port changes whenever STF recreates the worker**, so resolve it per session) and forwards input via `StfAdapter` (socket.io as STF's admin service account, `STF_ADMIN_EMAIL`). `screenSource: 'secure'` switches frames to the CpCapture helper, which also shows FLAG_SECURE windows (e.g. Google sign-in). `screenSource: 'scrcpy'` (高速, the web default where `VideoDecoder` exists) streams H.264 from the official scrcpy-server (`adapters/scrcpy.ts`; the browser approach follows ws-scrcpy, MIT): one server per device shared by all viewers (`control/scrcpy-hub.ts`: cached SPS/PPS + last key frame for late joiners, RESET_VIDEO for a fresh key frame, slow viewers skip to the next key frame, stop 5 s after the last viewer). The session sends `{type:'video',codec,width,height}`, then binary `[u8 flags 1=config 2=key][u64 pts][Annex B]`; `DevicePlayer.vue` decodes with WebCodecs (config prepended to key frames). Touch/keys/paste/typeSecure go through scrcpy control while it is the source (keys without a scrcpy keycode still go through STF), STF's screen socket is paused (`off`), and the device clipboard is polled once a second: changes go to viewers as `{type:'clipboard',text}` (own pastes are not echoed), `{type:'getClipboard'}` reads it on demand. If scrcpy can't start or dies, the session falls back to STF with `player.scrcpy_unavailable` / `player.scrcpy_ended`. **Relay** (external phones, only with `SCRCPY_RELAY_URL`): adbd there lacks `delayed_ack`, so one adb stream carries ~100 KB/s over the ~0.3 s tunnel. `CpRelay` (app_process as shell, versioned `/data/local/tmp/cprelay-<sha>.dex`, older versions removed at launch) connects the scrcpy sockets (video, then control) out to the relay listener (`control/scrcpy-relay.ts`, a separate `ws` server on 127.0.0.1, single-use hashed token in `X-Relay-Token`, 401 before upgrade otherwise) over the phone's own internet egress; bit rate `SCRCPY_BIT_RATE_RELAY`. If it doesn't connect within 10 s the hub starts a normal adb server instead; the `video` message reports `via` (`relay`|`adb`) and `relayError`.
- **Apps**: APK/split-bundle upload and batch install (`modules/apps`), app library (`modules/library`: import an installed app's APKs from a device, install elsewhere, preinstall on new devices), file upload to the phone's shared storage (`adb.pushMedia`).
- **Media library** (素材库, `modules/media`) on pluggable storage (`adapters/storage`: local disk or S3-compatible). Storage settings live in the `settings` table. The S3 secret is AES-256-GCM encrypted (`lib/secret-box.ts`, key derived from `JWT_SECRET`, so rotating it requires re-entering the secret) and write-only. Each asset remembers the backend it was stored on. `media_assets` has owner_type `public` (admin-managed; users see only `ready`, never `disabled`) or `user` (private to owner_id; admins see all), plus categories, case-insensitive tags and per-user favorites of public assets. Keys: `public|users/<id>/{images,videos,thumbnails}/<uuid>.<ext>`. Uploads are validated by extension + MIME + magic bytes and size (`MEDIA_*` config), hashed (sha256), stored as `processing`, then the device-less `media-process` job (`task-ops` queue, `enqueueTask`) computes metadata + a JPEG thumbnail/cover with sharp / ffprobe+ffmpeg. Delete = soft-delete row → delete file + thumbnail → hard-delete row (failed purges retried hourly); `assertMediaNotInUse` blocks deleting assets referenced by unfinished tasks (`tasks.ref_type/ref_id`). Deleting a user purges their private media first. Push to devices: `push-asset` op over adb from the API host (never through the device proxy).
- **Social accounts** (社交账号, `modules/social`): the operator's own platform accounts in `social_accounts` (never on `instances`), with per-user groups, case-insensitive tags and a per-account log `social_account_logs` (every field/status change and every device link/unlink, with from → to). Platforms come from a code registry (`platforms.ts`; `platform` is plain text, so a new platform needs no migration). Handles are unique per (platform, lower(handle)) across all owners. Users see only their own rows (others' are 404); linking a device needs a grant. The number of accounts per (device, platform) is capped (`social.limits` setting, admin `PUT /api/social/settings`, default 1), enforced under a per (device, platform) `pg_advisory_xact_lock`. The egress proxy is derived from the device's pool binding, never stored on the account. `deleteInstanceRow` unlinks and logs (FK `ON DELETE SET NULL` is the backstop); deleting a user cascades their accounts, groups and logs. No platform passwords are stored; status is set manually ("mark checked"). Automatic checks belong to the task centre and are not implemented here.
- **Comments & engagement** (评论互动, `modules/comments`): `comments` (local copy, unique per account + external id, `source` api|manual, thread by `parent_external_id`, linked to `publish_tasks` by external post id), `comment_sync_states` (cursor per account: YouTube page token, Instagram newest ISO time), `comment_tasks` (replies: draft → pending_review → approved/scheduled → sending → sent | awaiting_operator → sent/failed; rejected/cancelled), `comment_logs` (every transition and every rule block with its reason code), `comment_templates` (private or admin-shared). Task-centre jobs `comment-sync` and `comment-reply` (key `comment-reply:<id>:<round>`). Reply text is always written by a person; there is no bulk reply and no generated text. Rules (`settings` key `comments.rules`, admin): users' replies need approval by someone else (admins may self-approve), one active reply per comment (partial unique index), same normalized text ≤ N per account per window, sends per account per hour (over the limit the send is deferred to a new round, never dropped). API send only when the platform supports replies, the app is configured, the connection is `connected` and the comment came from the API; otherwise the reply goes to `awaiting_operator` and the operator records the outcome. Only 429 is retried; an attempt cut off mid-send fails as `comment.send_uncertain` instead of posting twice.
- **RBAC** (`modules/auth/rbac.ts`): two roles. `admin` sees everything; `user` sees only devices in `instance_grants` and may `view`/`control`/`operate` them. Creating/deleting devices, users/grants, the proxy pool and proxy binding, storage settings, audit log, library deletion and public media management are admin-only (`isAdmin`). The `builtin` user (ADMIN_USERNAME, flagged by the seed) cannot be deleted, disabled, demoted or have its password reset by others; the last enabled admin cannot be removed.
- **Dashboard + Settings** (`modules/dashboard`, `modules/settings`, `health.ts`, `modules/tasks/retention.ts`): `GET /api/dashboard` (the landing page `/dashboard`) runs every provider registered with `registerDashboardWidget(key, fn, { order })` (`dashboard/registry.ts`) in parallel; a provider gets `{ viewer, scope, admin, now, tz }` and must return RBAC-scoped aggregate data (one grouped query, no N+1) or null. Core widgets are in `dashboard/widgets.ts` (devices + cached host capacity, proxy pool (admin), social accounts/connections, tracked accounts with 7-day follower gains from snapshots, contents/publish runs with a 14-day per-day trend in the viewer's `tz`, task centre last 24 h, media, per-user breakdown (admin)). Admins may pass `?userId=` to see exactly what that user sees. New modules (e.g. comments) register their own widget and add a card in `DashboardView.vue`. `/settings` (admin) has tabs that reuse the existing settings APIs (storage, platform integrations, YouTube key, per-device social limits) plus read-only env values (`GET /api/settings/config`: publish defaults, media limits, audit retention), system info (`GET /api/settings/system`: real health checks shared with `/api/health`, versions, host capacity, STF) and task retention (`settings` key `tasks.retention`, default 90 days, `null` = keep): the hourly `tasks-cleanup` task (idempotent per hour) deletes finished tasks older than that with their logs, never unfinished tasks or tasks matched by a keep rule (`registerTaskKeepRule`; publish runs that are still unfinished). List pages accept the dashboard's filter query params (`?status=`, `?platform=`, `?exception=1`, … via `api/query.ts`).
- **Audit log** (`modules/audit`): an `onResponse` hook records every mutating `/api/` request (action table, target looked up before deletes, explicit exclusion list for read-like POSTs). Login is recorded explicitly. Details are allowlisted per action plus recursive redaction of `pass|secret|token|key|credential|authorization` keys; never log bodies verbatim. Writes are fire-and-forget; retention `AUDIT_RETENTION_DAYS`.
- **System management** (系统维护 `/system` admin, 连线监控 `/connections` RBAC-scoped; `modules/system`, settings key `system`: `backup {enabled, hour, keep}`, `logRetentionDays`, `historyRetentionDays`). `systemHourly()` (main.ts hourly + `POST /api/system/maintenance`) purges old log files and history rows, fails crashed backup rows and creates the daily backup task (from `hour`, API host local time, idempotency key `daily:<local date>`, so a day whose run failed is not retried: use "back up now"). **Backups**: device-less task `db-backup` (queue `system-ops`, concurrency 1) runs `${PG_DUMP_CMD} --format=custom --compress=6 --host … --dbname …` with the password only in `PGPASSWORD`, checks the `PGDMP` magic, stores the file via the active storage backend under `backups/` (row in `db_backups` with its backend), keeps the newest N ok backups; download is streamed (admin). pg_dump must be ≥ the server's major version (17); this Mac has none, so dev `.env` uses `PG_DUMP_CMD=env -u DOCKER_HOST docker exec -i -e PGPASSWORD cloudphone-dev-postgres-1 pg_dump` (`env -u` because `.env`'s DOCKER_HOST points at the VM). **Restore is manual**: stop the API, then `pg_restore --clean --if-exists --no-owner -h 127.0.0.1 -U cloudphone -d cloudphone <file>.dump` (dev: `DOCKER_HOST= docker exec -i cloudphone-dev-postgres-1 pg_restore --clean --if-exists --no-owner -U cloudphone -d cloudphone < <file>.dump`), then start the API. **Logs**: Fastify's pino `stream` is `logSink` (`logs.ts`): stdout unchanged, plus a redacted copy (audit key rule + `k=v`/Bearer/URL-credential text) in a ring of `LOG_RING_SIZE` lines and daily files `LOG_DIR/api-YYYY-MM-DD.log` (UTC); `GET /api/system/logs` (level/q/from/to, `date=` reads a file). **Connections**: `updateInstance` writes `instance_status_events` (status/adb changes, in its transaction); offline event = adb lost outside a transitional status, or status → error; `GET /api/system/connections` is one grouped query plus in-process scrcpy state (`scrcpyInfo`) and the adb round trip the monitor measures at most once a minute (`noteAdbRtt`). Device logs stay in the device log drawer.
- **Content + publish scheduler** (内容管理 / 定时发布, `modules/content`, `modules/publish`): `contents` (private per user; `stage` draft/ready/archived set by the editor, `status` derived from the stage and the publish tasks by `refreshContentStatus`), ordered `content_media` references to `media_assets` (own private or public ready media of the content's owner), case-insensitive `content_tags`. Distributing creates one `publish_tasks` row per target account (texts, options and the media id list are snapshots; the account's owner is the row's `user_id`; at most one unfinished row per content+account via a partial unique index; publishing an already published pair needs `republish`). Each scheduling round is one task-centre task of type `publish` (queue `publish`, `idempotencyKey publish:<id>:<attemptNo>`, `runAt`, `PUBLISH_MAX_ATTEMPTS`/`PUBLISH_TIMEOUT_MS`/`PUBLISH_RETRY_BACKOFF_MS`); reschedule/retry bump `attempt_no` and create a new task (the old one is detached: a run only proceeds if `publish_tasks.task_id` is its own id), so generic task-centre retry is disabled for this type. A run logs every check to `publish_logs` and the task log (owner, account active, media ready + platform capability table in `publish/platforms.ts`, no earlier publish, method available, device online + logged in when the method needs the device; device offline is retried, the rest fail at once) and calls a method from `publish/methods.ts` (`registerPublishMethod`; `api` preferred, `manual` registered for every platform). `manual` and API hand-overs end in `awaiting_operator`; the operator publishes by hand via remote control (optionally pushing the media with `/api/media/push`) and records the URL/ID or a failure reason. Media in unfinished publish tasks are protected by `assertMediaNotInUse`; contents with unfinished publish tasks can't be deleted or archived.
- **Errors and i18n**: throw via `lib/errors.ts` helpers with a stable `code` (+ `params`). Responses are `{ error, code, params }`; the web client (`errorText`) shows `t('errors.<code>')` with the raw message as fallback. All UI strings live in `apps/web/src/i18n/{zh-CN,en}.ts`; `en` is typed from `zh-CN`, so keys must match. Task/publish/comment log lines are stored in English; the UI translates them in `api/logText.ts` (exact strings + regexes → `logMsg.*`), so a new log message needs an entry there. Format dates with `toLocale*String(dateLocale())` so they follow the UI language. Theme (system/light/dark) comes from Ant Design tokens exported as `--cp-*` CSS variables (`components/ThemeVars.vue`); don't hard-code colours.

## STF / Android protocol gotchas (all verified)

- Touch events are consumed through a `SeqQueue`. They must be wrapped in `gestureStart` … `gestureStop` with consecutive `seq` numbers (mod 100), or they are silently dropped. `StfAdapter` owns the per-channel seq: assign it synchronously before any `await`, and share one in-flight socket connection.
- Per-key injection (`input.type`, fast typing) drops or reorders characters on redroid. Text goes through the `clipboard.paste` transaction. Passwords go through `typeSecure` (one char per 120 ms, never touches the device clipboard).
- Reading the device clipboard via STF fails on Android 10+ (background app denied); the scrcpy source reads it (scrcpy-server runs as shell).
- `adb shell` runs as uid 2000. Reads of app-private data use `su 0` (redroid is userdebug). `sqlite3` crashes on redroid, so the GSF ID is read from GMS `shared_prefs/Checkin.xml`.
- **Screen capture of FLAG_SECURE windows** needs `captureSecureLayers` as the system uid: CpCapture runs via `su 1000 … app_process`. Processes backgrounded over adbkit's `shell:` connection get killed when it closes (nohup/setsid don't help), so the API keeps the helper in the foreground of a held adb shell stream per device.
- **MediaStore**: files written via adb sync get indexed with `is_pending=1` (invisible to other apps). Clear it per row by `_id`; selection on `_data` is ignored for shell callers, so look rows up by `_display_name` + `relative_path`. `pushMedia` verifies `is_pending=0`.
- **Android's netd flushes `ip rule`s**, so sing-box `tun`/`auto_route` can't capture app traffic, and sing-box's `auto_redirect` fails in this environment. Use plain nftables in the netns. sing-box's own sockets need `default_mark` and `default_interface: eth0` (netd's `oif eth0` rules). In the filter chain, match redirected traffic by `ip daddr 127.0.0.0/8` (its `oif` is still the old one at that hook).
- Android 13 `dumpsys activity` uses `ResumedActivity:` (12 used `mResumedActivity`). Launcher icon positions differ between versions (see the `LAYOUT` map in the smoke test).
- Changing system locale restarts zygote (not the container or adbd). Apply the locale **before** other settings, because SettingsProvider writes just before a zygote restart get lost.
- `logcat -t N` applies per buffer; trim server-side.
- **scrcpy-server v5.0.1 wire format** (verified on redroid 13 and the BitBrowser phone): the first arg must be the exact server version. With `tunnel_forward=true` the server listens on `localabstract:scrcpy_<scid %08x>`; connect video first (only the first socket gets the dummy byte `0x00`), then control. Video: `u32 codec id` (`h264`; 0 = disabled, 1 = config error), then 12-byte headers: a **session packet** (bit 63 set: u32 flags, u32 width, u32 height, new in v5, sent before each encoder (re)start, e.g. after RESET_VIDEO or rotation), or a frame header (u64 pts, bit 62 = config, bit 61 = key frame; u32 size). Touch events must carry the current video size from the session packet, or they are silently ignored. `cleanup=true` (default) deletes the jar at start, so we pass `cleanup=false` to keep the versioned jar in /data/local/tmp. `power_on=false` so a viewer never wakes the screen. GET_CLIPBOARD only answers with `clipboard_autosync=false`, and sends nothing while the clipboard is empty. The encoder emits frames only when the screen changes, so low fps on a static screen is normal. Encoders seen: redroid uses software (encoding runs in the media codec service, not in the app_process); the BitBrowser OPPO uses `c2.rk.avc.encoder`.
- scrcpy shows FLAG_SECURE windows black, just like STF (checked on Settings' PIN screen, `fl=… SECURE`). Only the `secure` source (CpCapture as uid 1000) shows them. Google's sign-in email step is not FLAG_SECURE on redroid 13.
- `jp.co.cyberagent.stf*` packages are STF's on-device agents and must never be uninstalled (`isProtectedPackage`).
- Google Workspace accounts may require a screen lock and device management (`DeviceManagementScreenlockRequired`); that is the organisation's policy, not a platform bug, and must not be bypassed.
