# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Cloud-phone management platform: a Node.js/TypeScript control plane that manages Android containers (redroid) on a Linux host and reuses DeviceFarmer STF for device management and remote control. npm workspaces monorepo: `apps/api` (Fastify), `apps/web` (Vite + Vue 3 Composition API + Ant Design Vue + Pinia + vue-i18n). The UI is bilingual (zh-CN/en); docs and many code comments are Chinese. Devices are called 设备 in the UI and `instances` in code.

## Commands

```bash
# Dev dependencies (Postgres on 5432, Redis on 6380: 6379 is taken on this machine)
docker compose -f docker-compose.dev.yml up -d
docker compose -f infra/stf/docker-compose.yml up -d --build   # STF + RethinkDB + adb server
limactl start redroid                                          # Linux VM that runs redroid (see below)

npm run dev:api          # tsx watch, reads ../../.env; http://127.0.0.1:3000, /api/health checks every dependency
npm run dev:web          # Vite on :5173, proxies /api (incl. WebSockets) to the API
npm run typecheck        # tsc (api) + vue-tsc (web); there is no linter
npm run db:migrate && npm run db:seed    # migrate also runs idempotent TS data migrations (src/db/*-migration.ts); seed ensures the built-in admin (ADMIN_USERNAME), password only on creation
ADMIN_RESET_PASSWORD=1 npm run db:seed   # deliberately reset the built-in admin password to ADMIN_PASSWORD
cd apps/api && npx drizzle-kit generate --name <name>   # after editing src/db/schema.ts; never edit old migrations
```

If the API was started without `watch` (plain `npx tsx --env-file=../../.env src/main.ts`), backend changes need a restart.

## Production deployment (docs/10-deployment.md)

Blue-green on one Linux host with Docker Compose: shared Postgres/Redis/Caddy (`deploy/compose.shared.yml`) + STF (`infra/stf` + `deploy/stf.override.yml`); each colour = api + web of one version (`deploy/compose.app.yml`, host networking, per-colour loopback ports). Images `ghcr.io/<owner>/<repo>-{api,web}:<version>` from `deploy/docker/*.Dockerfile` (context = repo root). GitHub: Actions → Deploy (`.github/workflows/deploy.yml`, manual; branch via "Use workflow from", `action` deploy|rollback, `version`, `rollback_steps` 1|2, `environment`). GitHub workflows are manual only (`workflow_dispatch`); never add push/PR/schedule/workflow_run triggers back. Deploy runs share one concurrency group `deploy` (no cancel-in-progress; GitHub keeps only one pending run per group, a newer one replaces it).

```bash
/srv/cloudphone/deploy/deploy.sh <version>   # migrate once → start idle colour → /api/ready → caddy reload → drain → stop old
/srv/cloudphone/deploy/rollback.sh <1|2>     # re-deploys a recorded older version the same way
/srv/cloudphone/deploy/status.sh
DOCKER_HOST= docker buildx build -f deploy/docker/api.Dockerfile -t cp-api:test --load .   # local image build (DEX_HELPERS=0 skips the SDK download)
```

- **Migrations must stay backward compatible (expand/contract)**: the old colour runs on the new schema until the switch, and a rollback runs old code on it (migrations are never undone). Only add (tables, nullable/defaulted columns, indexes) in a release; drop/rename/NOT NULL only in a later release once no rollback target uses the old shape.
  - **Exception 0037 (persona reset, owner decision 2026-11-18)**: the owner had all persona data wiped instead of migrated. Migration 0037 is data only (no column change): it clears `social_accounts.persona_id` (and leftover `group_id`), deletes templates with a persona, clears the legacy `comment_templates.persona` texts (so `persona-data-migration.ts` / `social-group-data-migration.ts` cannot re-create personas) and deletes every persona; `contents.ai_generated` keeps its persona name/id as history. `personas.brief` keeps its name and now holds the new style shape, so the old colour still selects every column and keeps working during the switch (it may show the new style values as its old brief fields); no downtime needed. A rollback cannot bring the deleted personas back. Recreate test personas with `scripts/demo-seed-personas.ts`.
- Background work (task workers, monitor + BitBrowser tunnels, retention, hourly schedulers) runs only in the Redis-lease leader when `BACKGROUND_WORK=leader` (`lib/leader.ts`; dev default `always`). The old colour releases the lease last in its SIGTERM shutdown, after its running tasks. `/api/ready` (API + Postgres + Redis, with version/colour/background role) gates the switch; `/api/health` stays the full dependency check.
- New task types on an existing queue can be failed as `task.unknown_type` by the old leader during the few drain seconds; prefer a new queue for a new type.

## Environment facts that are not obvious

- **redroid cannot run in Docker Desktop**: its kernel has no binder. Android runs in the Lima VM `redroid` (`infra/lima/redroid-host.yaml`, Ubuntu arm64, `binder_linux`, nftables modules). The API talks to the VM's Docker through the forwarded socket `~/.lima/redroid/sock/docker.sock` (`DOCKER_HOST` in `.env`). Sourcing `.env` in a shell therefore redirects the `docker` CLI to the VM, not to Docker Desktop.
- Device adb ports (5555–5604) are published in the VM (on the network sidecar) and forwarded by Lima to the Mac's 127.0.0.1. STF's adb container reaches them as `host.docker.internal:<port>`, which is the device serial (`ADB_DEVICE_HOST`).
- Google's emulator has **no Linux arm64 build**, so the `emulator` engine (`adapters/runtime/emulator.ts`) is code-only and untested. It needs an x86_64 host with `/dev/kvm`.
- **Android 16 does not boot on this host**: redroid 16's gralloc needs ashmem, which Linux ≥5.18 (here Ubuntu 6.8) lacks. The `redroid-16-gapps` profile carries a `blockedReason`. Details and options: `docs/06-android-upgrade-plan.md`.
- GApps images are built locally from official, signature-verified MindTheGapps: `infra/redroid-gapps/build.sh` (`ANDROID=13|16`; `verify_jar.py` for JAR-signed 13 packages, `verify_ota.py` for OTA whole-file-signed 16 packages, then `stage.py` and the Dockerfile template). Never use third-party GApps rebuilds.
- scrcpy-server (`infra/device-tools/scrcpy/`, official Genymobile release v5.0.1, SHA-256 pinned in `fetch.sh` and the README): `fetch.sh` downloads it into the gitignored `out/` (`SCRCPY_SERVER_PATH`). Rerun it on a fresh checkout; without it the 高速 source falls back to STF.
- The app_process helpers (`infra/device-tools/capture/` → `out/cpcapture.dex`, `infra/device-tools/relay/` → `out/cprelay.dex`) are built by their `build.sh` via the shared `build-dex.sh` in a throwaway JDK container from official SDK packages (`SDK_DL` dir with `platform-33-ext3_r03.zip` and `build-tools_r34-linux.zip`, sha1 from `dl.google.com/android/repository/repository2-3.xml`; `infra/device-tools/fetch-sdk.sh` downloads and verifies them, `compile-dex.sh` is shared with the API image). No lambdas (android.jar has no LambdaMetafactory). `out/` is gitignored, so rebuild on a fresh checkout.
- **scrcpy relay (experimental, external phones)**: set `SCRCPY_RELAY_URL=wss://<public host>/scrcpy-relay` and expose only `127.0.0.1:SCRCPY_RELAY_PORT` (3010), e.g. `ngrok http 3010` in dev (the free ngrok dev domain is fixed; free plans cap monthly data; use `--region eu`: measured from this Mac the `in` region was ~80 ms worse); in production a TLS reverse proxy routes `/scrcpy-relay` to it (no ngrok). Never expose the API port, always wss. The relay connection leaves through the phone's bound proxy like any app (BitBrowser applies it below Android). Restarting the API also restarts the BitBrowser SSH tunnels; the first session after a restart may time out on `ready`.

## Architecture

The API is the only thing browsers talk to. It enforces RBAC and relays STF; STF is never exposed to end users.

- **Two layers per device, deliberately separate.** Container lifecycle is `AndroidRuntime` (`adapters/runtime/`: `DockerHost` holds shared Docker plumbing and helper containers; `DockerRuntime` base; `RedroidRuntime`/`EmulatorRuntime` only define their container spec; `runtimeFor(engine)`). Device control is `AdbAdapter` plus `StfAdapter`. `modules/instances/ops.ts` orchestrates both: create sidecar + container, start, adb connect, boot check *via adb* (engine-agnostic), `applyDeviceSettings`, wait for STF ready, claim, then enqueue preinstall apps.
- **Network sidecar per device** (`adapters/runtime/network.ts`, `modules/network/singbox.ts`): a sing-box container owns the device's netns and adb port; the Android container joins it (`NetworkMode: container:`). With a proxy, nftables redirects TCP and DNS to sing-box and the filter chain's `policy drop` is the kill switch (no direct fallback, no IPv6, no non-DNS UDP). Proxy changes rewrite config + rules and SIGHUP (no Android restart). Legacy devices without a sidecar are converted when a proxy is first bound.
- **Tracked accounts** (追踪账号, `modules/tracked`): external public profiles a user observes, separate from their own social accounts. `tracked_accounts` (private per `user_id`, admins see all with an owner filter, others get 404; unique per user+platform+normalised handle; lowercase `tags text[]` with GIN index (the only grouping: the former free-text `category` was folded into tags by `src/db/tracked-category-data-migration.ts`, run by `db:migrate`: trimmed, lowercase, cut to 32 chars, deduplicated, then `category` set null so reruns are no-ops; the column and `tracked_accounts_user_category_idx` are no longer read or written, drop them in a later release; an old client's `category` in a body is stripped by zod, the `category` filter and facet are gone), `favorite` flag since rows are private), `tracked_account_snapshots` (followers/following/posts/views over time, source api|manual; list shows latest + delta vs. previous follower count) and `tracked_posts` (unique per account+external id; upsert keeps first_seen_at and known values). **Manual entry was removed** (owner decision 2026-11-18): no POST of snapshots/posts any more (404); old `manual` rows stay listed and deletable. Snapshot `source` api|device|manual(legacy), `approx text[]` = metrics the app abbreviated (UI shows 约/≈), `tracked_accounts.verified`. `platforms.ts` is the registry: URL/handle normalisation (youtube @handle or /channel/UC…, instagram.com/<user>, tiktok.com/@<user>; coded errors for other hosts/paths) and an optional `TrackedSource` (`kind` api|device, `capabilities`, `fetchProfile(acc, ctx)`, `fetchRecentPosts`). YouTube: official API (`youtube.ts`, Data API v3 channels/playlistItems/videos, base URL `YOUTUBE_API_BASE`, key in `settings` key `youtube`, secret-box encrypted, write-only via admin `GET/PUT /api/settings/youtube`). TikTok: no source (`dataMode` `manual_only` = no source, no refresh/schedule). **Instagram: 云手机采集** (see below). Refresh = device-less `tracked-refresh` job (`enqueueTask`, refType `tracked_account`) running `refreshTrackedAccount(id)` (periodic runs: see 定时采集 below); platforms without a source complete as a no-op (the web UI offers 刷新 / 批量刷新 / 定时采集 only when `dataMode !== manual_only`; `*_unconfigured` disables them), paused/in-progress/unconfigured (no key, collector unset/halted) are refused with codes, failures set status `error` + `last_error_code`.
- **云手机采集** (Instagram tracked accounts read in the Instagram app; owner decision 2026-11-18, replaces the former "never scrape" rule for exactly this case): `tracked/instagram-device.ts` + `tracked/collector.ts`. Admin picks the collector device per platform (settings key `tracked.collectors`, `GET/PUT /api/settings/tracked-collectors[/:platform] {instanceId|null, resume}`, audited `settings.tracked_collector`; UI 设置 → 追踪账号 (device choice only), next to the YouTube key, since both are admin data-source settings; pace, halt state and 恢复 are on the 风控 page). A visit: device running + adb `device` (else `tracked.collector_offline`), `pm path com.instagram.android` (`tracked.collector_app_missing`), `am start -a VIEW -d https://www.instagram.com/<handle>/ -p com.instagram.android`, poll `uiautomator dump` into `/data/local/tmp/cp-ig-<rand>.xml` (read + deleted each time) for ≤ 15 s until the header ids (`profile_header_familiar_{followers,following,post_count}_value`, `action_bar_title` = handle, `action_bar_title_verified_badge`, `profile_header_full_name_above_vanity`, bio = first text under `profile_user_info_compose_view`) show, then HOME (also after failures). Counts: `parseCompactCount` (万/萬/亿/億/千, K/M/B, commas, decimals; a unit = approximate). Codes: `collector_logged_out` (login screen), `collector_profile_unavailable` (a non-existent user leaves the profile shell empty with a spinner; verified live), `collector_timeout`, `collector_parse_failed` (task log keeps ≤ 300 chars of ids/texts, never the dump), private accounts are stored when the counts show. A challenge / verification / rate-limit screen (`collector_challenge`) **halts the device** (settings key `risk.halts` per device id, `haltDevice`; halt fields on an old `tracked.collectors` entry are read as that device's halt): every refresh `tracked.collector_halted`, scheduler skips, account checks on it skip, and alert kind `collector.blocked` (refType instance, admins + device grants, channels too) until an admin resumes it on the 风控 page (`POST /api/risk/devices/:id/resume`, or the setting's `resume`; picking another device leaves the old one halted). Collector problems (challenge, logged out, parse failed, timeout, app missing) are written to 风控记录. Only the login/challenge/not-available *texts* are heuristics not yet seen live. Limits (`withDevice`, per device, shared by every automatic operation on that phone: collector visits and account checks): one operation at a time (Redis lock), ≥ minIntervalSec between visits and ≤ maxPerHour per rolling hour (Redis sorted set; last visit kept for the 风控 page), no visit while a remote-control session or scrcpy viewer is on the device (in-process `controlSessionCount` / `scrcpyActive`; `tracked.collector_busy`, retried after busyRetrySec). The values are the 风控 setting `risk.device` (`risk/settings.ts`, read per visit with a 5 s cache); `TRACKED_DEVICE_MIN_INTERVAL_SEC` (30) / `_MAX_PER_HOUR` (60) / `_BUSY_RETRY_SEC` (300) are only its defaults. Each of these ends the attempt as outcome `deferred` and creates the next `tracked-refresh` at the allowed time (key `deferred:<task>`, ≤ 30 deferrals): never dropped, no worker sleeps. Never anything else on the device for a profile refresh: no taps, no typing, no likes/follows/comments, no fingerprint/identity changes, no captcha solving, no account rotation, no randomised "human" behaviour. Posts and comments are read by the separate feed collection (帖子与评论, below).
- **帖子与评论** (account feed, `modules/feed`, owner decision 2026-11-18): every social account (on its own cloud phone) and every tracked Instagram account with 定时采集 on (on the collector phone) gets its newest posts and their first comments read in the Instagram app, read only. **Screens** (`feed/ig-ui.ts`, probed on bit-ins-02, IG 433, zh-CN; dumps of the probe are the parser reference): profile deep link → header (posts count; 0 → done) → tap the first grid item (`#image_button`) → `dumpsys activity top` lists the grid's media ids (`ContextualFeedFragment.ARGUMENT_MEDIA_ID_LIST=[<pk>_<owner pk>…]`, pinned first). **The media pk is the stable post id**: top bits = creation time (ms since 1314220021721, exact `published_at`), base-64 (IG alphabet) = shortcode → permalink `https://www.instagram.com/p/<sc>/`, which opens the post in the app; newest N = largest pks (pinned posts don't count). Post screen: `#row_feed_view_group_buttons` (count button after `#row_feed_button_like` / `#row_feed_button_comment`; a photo's media desc "…, 14,563次赞, 57条评论" gives exact counts; units → `approx`), caption = the IgTextLayoutView text after the handle, header desc "…发布了video|carousel|photo" = media type; `IgSessionManager.SESSION_TOKEN_KEY=…:<pk>` = the logged-in account's numeric id. Comments sheet (comment button): rows without ids (avatar "前往X的主页"/"查看X的快拍", "X表示<text>", time "11小时前" → approximate time, "回复", "N次赞", "查看另外N条回复"); scrolled until `feedCommentsPerPost`; IG shows no comment id, so the stable id is `commentKey` = sha256(post pk, author, normalised text) (the same author writing the same text twice on one post collapses). English UI strings are guesses. **Task** `feed-collect` (own queue `feed-collect`, 1 attempt, 15 min) under `withDevice` with `weight` = posts + 2 (screens counted in the hourly cap) and a 15 min lock; pace defers re-create it (`deferred:<task>`); challenge → device halted (`risk.halts`, source feed) + 风控记录; offline → task fails `feed.offline`. Writes: social → `social_account_posts` (now also `source` device, `approx`, `comments_fetched_at`; upsert keeps first_seen_at) + `comments` (source `device`, so 评论互动 lists them; counts updated, status kept); tracked → `tracked_posts` (source device, `media_type`, `approx`) + new `tracked_post_comments` (unique post + id, `position` = app order, read only). Schedule: 风控 `feedCollectHours` (default 24, null = off), hourly `scheduleFeedCollects`, hash offset per account, key `feed:<social|tracked>:<id>:<slot>`; running not-halted phones only. 立即采集 `POST /api/social/accounts/:id/collect` / `POST /api/tracked-accounts/:id/collect` (202; `feed.no_device`, `feed.unsupported_platform`, `tracked.collector_unset`, 409 `feed.device_halted` / `feed.in_progress`), audited `feed.collect*`. Feed API `GET /api/social/accounts/:id/feed` / `GET /api/tracked-accounts/:id/feed?limit&offset&comments` (动态 = counter readings with changes, new posts, collection runs, replies; posts newest first with the first comments (threads) + total, collection state incl. halted / test mode) and `GET …/posts/:postId/comments?limit&offset`; RBAC of each module (others 404). Web: social row click → `SocialAccountFeedDrawer` (动态 / 帖子 / 回复记录), tracked drawer gets 动态 + feed posts with 「评论」/「回复」 (see 评论追踪账号的帖子 below) + 回复记录; both 回复记录 tabs are `components/feed/FeedReplyTable.vue`; comments folded with `components/comments/FoldToggle.vue` (shared with 评论互动).
- **Account analytics** (账号分析, `modules/analytics`, page `/analytics`): read only. The data source is the **automatic account check** on each account's cloud phone (社交号自动检测, below): it writes followers/following/posts into today's `social_account_stats` row (source `device`, `approx text[]` = abbreviated by the app, shown as ≈). The official-API task `account-stats` and manual entry were removed on 2026-11-18; their rows (source api|manual) stay readable. Numbers of the operator's OWN social accounts in `social_account_stats` (unique per account + UTC `day`; counters followers/following/posts + lifetime `total_views`/`total_likes`, day activity views/likes/shares/comments, `missing`) and own posts in `social_account_posts` (history only; scripts seed via `scripts/lib/analytics-seed.ts`). No banner; without rows the page shows a plain empty state ("暂无数据 · 绑定云手机的社交号会被自动检测并记录数据"); never fabricate numbers. Per-day gains come from `lib/counter-deltas.ts` (value − previous non-null reading via `lag`; also used by the tracked-accounts dashboard gain); views/likes per day fall back to lifetime-total differences. REST `/api/analytics/summary?days=1..90&ownerId&platform`, `/api/analytics/accounts/:id` (series), `GET …/posts?sort=published|likes|comments&limit&offset` (linked to `publish_tasks` at read time: account + external_id, published); RBAC = social accounts (users own, others 404). Dashboard widget `analytics` (7-day gains/views/likes/comments/shares). Charts plot days without data as gaps (`LineChart` `v: null`), never 0.
- **Proxy pool** (代理 IP, `modules/proxies`, admin only): proxies in `proxies` with `kind` static|mobile (page tabs; `dynamic` was removed, migration 0028 turned such rows static; `?kind=` filter, `kindCounts`; device auto-assignment ignores kind) (password AES-256-GCM via `secret-box`, write-only; status + `last_check` from a check run on the API host through the proxy with `socks-proxy-agent`/`https-proxy-agent` against api.ipify.org + ipinfo.io). A device references one via `instances.proxy_id` (UNIQUE: one proxy ↔ at most one device; FK `ON DELETE RESTRICT`, delete of a bound proxy is a 409). The sidecar config is built from the pool entry at apply time (`resolveProxyConfig` decrypts). `POST /api/proxies/test` checks an unsaved config the same way (stores nothing, audit-excluded; with `id` an empty password falls back to the stored one only for the same username). Binding (`PUT /api/instances/:id/proxy {proxyId}`) is admin only; users see their devices' proxy without username/password (`publicInstance()`). Device creation takes `proxyMode: auto|pick|none`; auto picks free ok/unchecked proxies with `FOR UPDATE SKIP LOCKED` inside the insert transaction. Editing a bound proxy's endpoint/credentials re-applies it to the device (set-proxy task). Batch (批量栏 on the page: 检测 / 改类型 / 删除): `POST /api/proxies/batch {ids 1..500, action delete|set-kind, kind}` locks the rows; any unknown id = 404 for the whole batch, nothing changed; delete skips bound proxies (`skipped: [{id, code: proxy.bound, params}]`); audited as `proxy.batch_delete` / `proxy.batch_set_kind` with counts only. Old inline `instances.proxy` values were moved into the pool by `src/db/proxy-data-migration.ts`, run by `db:migrate` around the schema migrations.
- **Device sources** (设备来源, `modules/sources`, admin only): external phones next to local containers. `device_sources` (type, name, config jsonb without secrets; restrict-deleted while devices use it) and `instances.source_id` + `external_id` (unique per source). One `SourceDriver` per type (`types.ts`: config schema, test, listPhones, optional power on/off/isOn, openAdb/closeAdb); `ops.ts` (`ext*`) and the monitor's separate 15 s loop only call the driver, so a new kind is one driver file. The driver makes the phone's adbd reachable on `EXTERNAL_ADB_BIND:<5700–5799>` (= `adb_port`), so adb/STF/remote control/apps/social code is shared unchanged. Adding (`POST /api/instances/external`) never powers on; delete only removes the device from the platform. External phones refuse the proxy pool and device settings (`instances.engine_unsupported`). **BitBrowser** (`sources/bitbrowser.ts`, `adapters/bitbrowser.ts`, `adapters/bitbrowser-tunnel.ts`): the BitBrowser client's local API (Windows/Mac; POST JSON, ≤1 req/s, serialised per address); power-on is billed until shutdown; adb = `ssh -N -L` child per phone to BitBrowser's gateway, password fetched fresh from `/phone/adb/get` and passed only via an askpass env var, renewed 30 min before the ~28 h grant expires. Source config: `apiUrl`, optional `apiKey` (the client's "Local API Token", sent as `x-api-key`; secret fields of a driver (`SourceDriver.secrets`) are stored sealed as `<field>Enc`, never returned, only `<field>Set`; edits without the field keep it, null clears it — `sources/index.ts`), optional `timeZone` (IANA zone of the client machine; the adb grant's expiry is that wall clock). Reads (list/running/adb get) time out after 8 s (power on 120 s, off/enable 60 s); each client keeps a health record (`GET /api/device-sources` → `health`, shown in the source picker) and the monitor skips a source's remaining phones for the round once its client is down. Tunnel renewal fetches new credentials before replacing a working tunnel; ssh is resolved through PATH by the API itself (a broken PATH entry, e.g. a self-referencing `node_modules` symlink, made spawn fail with ELOOP). The client binds 0.0.0.0 without auth unless its token is on: firewall it. Never wrap 一键新机 (`profile/recover`) or fingerprint editing; locale/time zone come from the BitBrowser profile and are re-applied on every boot.
- **Profiles** (`src/profiles.ts`) map a profile id to engine, image, `gapps`, `requiresKvm`, `memEstimateMb` and optional `blockedReason`. `GET /api/profiles` reports availability. Device creation runs a host memory capacity check.
- **All device mutations go through BullMQ** via the task centre (`modules/instances/queue.ts` registers one handler per op on the `instance-ops` queue; `enqueue`/`enqueueTask` are thin wrappers over `createTask`): create, start, stop, restart, delete, install-apk, uninstall-app, apply-settings, set-proxy, import-app, push-asset (plus device-less jobs such as media-process on `task-ops`). A failure of a device-only op (`DEVICE_OPS`) must not mark the device `error`. Routes reject actions on busy statuses.
- **Platform scope** (`ENABLED_PLATFORMS`, default `instagram`; comma list or `all`): the single switch, read by `lib/platforms-enabled.ts` (`isPlatformEnabled`/`assertPlatformEnabled`). Every registry keeps all platforms' code and filters by it: option lists (`/api/platforms` = `enabled` + `features` only, social/publish/tracked platform lists) show enabled ones only; anything new on a disabled platform (account, tracked account, limits, YouTube key, distribution/retry, tracked refresh, trending settings/refresh) is a 400 `platform.disabled`; existing rows stay listed, schedulers skip them (tracked schedule, publish runs fail `platform.disabled`). Trending needs `youtube` (else `trending.unavailable`, no widget). The web reads `/api/platforms` once (`stores/platforms.ts`) for every platform list/tab/menu. Add a platform = its registry entries (`social/platforms.ts`, `publish/platforms.ts`, `tracked/platforms.ts`, the web brand icon in `components/social/platformMeta.ts` (`PlatformIcon`/`PlatformTag`)) + list it in `ENABLED_PLATFORMS`. Regression checks for the other platforms run with `ENABLED_PLATFORMS=all` (API and script).
- **Platform integrations** (平台接入, official platform APIs: OAuth connect, API publishing, comment sync/replies, account analytics, 号状态监控 account checks): **removed on 2026-11-18 by owner decision.** `modules/platforms` only keeps `GET /api/platforms` (platform scope for the web). Publishing and comment replies are manual (operator on the phone), comments are entered by hand; 账号分析 gets its numbers from the automatic account check on the cloud phone (社交号自动检测, new task type `account-device-check`; the old name `social-account-check` is not reused). Kept (not OAuth): the YouTube Data API key (tracked accounts, trending) and the collector phone. LEGACY until the next release (expand/contract, nothing reads or writes them): tables `platform_connections` (rows deleted, i.e. no tokens at rest) and `comment_sync_states`, the `settings` row `platform.apps`. `src/db/official-api-removal-migration.ts` (run by `db:migrate`, idempotent) deleted the connections, cancelled unfinished `account-stats` / `comment-sync` / `social-account-check` tasks (task log `cancelled: official platform APIs removed`), set waiting publish rounds with method `api` back to manual, and removed the alert kind `connection.expired` (notifications, alert states, channel kinds; a channel left with no kind is disabled) and `accountCheckHours` from the rules. Drop the two tables, the setting and the cancelled task types' i18n labels in the next release.
- **Task centre** (任务中心, `modules/tasks/core.ts`): the single scheduler for every background job. Modules call `registerTaskHandler(type, { run(ctx), queue, concurrency, timeoutMs, maxAttempts, backoffMs, cancellable, retryable, beforeRetry, onFailure })` at import time and `createTask({ type, userId, instance, label, refType, refId, payload, runAt, idempotencyKey, ... })`. `tasks` holds scheduling state only (statuses pending/scheduled/running/success/failed/cancelled; payload/result jsonb, attempts, last `error` + `error_code`); `task_logs` gets a line per transition plus `ctx.log`. BullMQ job id = task id, data `{taskId}`; the worker reloads the row and every transition is status-guarded. Retries: exponential backoff up to max_attempts (task returns to pending between attempts); timeout fails the attempt (`task.timeout`); cancel removes pending/scheduled jobs, running tasks get `cancel_requested` + `ctx.signal` (via the event bus; device ops just finish). Manual retry = new task with `retry_of`. Idempotency key unique per (type, key) for all time. Crash safety: workers use `maxStalledCount: 0`, a redelivered job whose task is still `running` fails it as `task.interrupted` (never reruns non-idempotent work); `reconcileTasks()` at startup fails running tasks whose job is gone and re-enqueues pending/scheduled ones. Payload is visible in the UI: never put secrets in it. REST `/api/tasks` (filters, stats, detail+logs, cancel, retry; users see own tasks + tasks on granted devices, else 404); events `task.updated` / `task.log` omit payload/result. Test-only type `test.echo` is registered only with `TASKS_TEST_HANDLERS=1`.
- **Every device/task write goes through `modules/instances/repo.ts`**, which publishes on a Redis pub/sub bus (`lib/events.ts`). `/api/events` WebSocket forwards it to browsers, filtered by RBAC.
- **Monitor** (`modules/monitor/monitor.ts`, every 5 s) reconciles Docker, sidecar, adb and STF state and re-attaches dropped adb connections. STF's `ready` flag lags reality, so health is decided by adb and Docker. Google health (`modules/google/health.ts`) runs at most every 60 s for GApps profiles; proxy egress checks every 5 min. Egress (`instances.proxy_status`: IP, latency, DNS, ipinfo geo validated against the IP) is measured by one shared script (`lib/egress.ts`): local devices in the sidecar netns, external phones on the phone itself over adb (`adb.egress`, curl; AOSP redroid has no curl), via `modules/instances/egress.ts` `checkEgress` (one run per device at a time). The external loop runs it in the background every 5 min per running phone; `POST /api/instances/:id/proxy/check` works for both.
- **Remote control**: `/api/instances/:id/session` WebSocket. First message `{type:"auth",token}`, then RBAC, then claims the device in STF. It relays JPEG frames from STF's screen WebSocket (`display.url`, whose **port changes whenever STF recreates the worker**, so resolve it per session) and forwards input via `StfAdapter` (socket.io as STF's admin service account, `STF_ADMIN_EMAIL`). `screenSource: 'secure'` switches frames to the CpCapture helper, which also shows FLAG_SECURE windows (e.g. Google sign-in). `screenSource: 'scrcpy'` (高速, the web default where `VideoDecoder` exists) streams H.264 from the official scrcpy-server (`adapters/scrcpy.ts`; the browser approach follows ws-scrcpy, MIT): one server per device shared by all viewers (`control/scrcpy-hub.ts`: cached SPS/PPS + last key frame for late joiners, RESET_VIDEO for a fresh key frame, slow viewers skip to the next key frame, stop 5 s after the last viewer). The session sends `{type:'video',codec,width,height}`, then binary `[u8 flags 1=config 2=key][u64 pts][Annex B]`; `DevicePlayer.vue` decodes with WebCodecs (config prepended to key frames). Touch/keys/paste/typeSecure go through scrcpy control while it is the source (keys without a scrcpy keycode still go through STF), STF's screen socket is paused (`off`), and the device clipboard is polled once a second: changes go to viewers as `{type:'clipboard',text}` (own pastes are not echoed), `{type:'getClipboard'}` reads it on demand. ## STF / Android protocol gotchas (all verified)

- Touch events are consumed through a `SeqQueue`. They must be wrapped in `gestureStart` … `gestureStop` with consecutive `seq` numbers (mod 100), or they are silently dropped. `StfAdapter` owns the per-channel seq: assign it synchronously before any `await`, and share one in-flight socket connection.
- Per-key injection (`input.type`, fast typing) drops or reorders characters on redroid. Text goes through the `clipboard.paste` transaction. Passwords go through `typeSecure` (one char per 120 ms, never touches the device clipboard).
- Reading the device clipboard via STF fails on Android 10+ (background app denied); the scrcpy source reads it (scrcpy-server runs as shell).
- `adb shell` runs as uid 2000. Reads of app-private data use `su 0` (redroid is userdebug). `sqlite3` crashes on redroid, so the GSF ID is read from GMS `shared_prefs/Checkin.xml`.
- **Screen capture of FLAG_SECURE windows** needs `captureSecureLayers` as the system uid: CpCapture runs via `su 1000 … app_process`. Processes backgrounded over adbkit's `shell:` connection get killed when it closes (nohup/setsid don't help), so the API keeps the helper in the foreground of a held adb shell stream per device.
- **MediaStore**: files written via adb sync get indexed with `is_pending=1` (invisible to other apps). Clear it per row by `_id`; selection on `_data` is ignored for shell callers, so look rows up by `_display_name` + `relative_path`. `pushMedia` verifies `is_pending=0`.
- **Android's netd flushes `ip rule`s**, so sing-box `tun`/`auto_route` can't capture app traffic, and sing-box's `auto_redirect` fails in this environment. Use plain nftables in the netns. sing-box's own sockets need `default_mark` and `default_interface: eth0` (netd's `oif eth0` rules). In the filter chain, match redirected traffic by `ip daddr 127.0.0.0/8` (its `oif` is still the old one at that hook).
- Android 13 `dumpsys activity` uses `ResumedActivity:` (12 used `mResumedActivity`). Launcher icon positions differ between versions (see the `LAYOUT` map in the smoke test).
- Changing system locale restarts zygote (not the container or adbd). Apply the locale **before** other settings, because SettingsProvider writes just before a zygote restart get lost.
- `logcat -t N` applies per buffer; trim server-side.
- **scrcpy-server v5.0.1 wire format** (verified on redroid 13 and the BitBrowser phone): the first arg must be the exact server version. With `tunnel_forward=true` the server listens on `localabstract:scrcpy_<scid %08x>`; connect video first (only the first socket gets the dummy byte `0x00`), then control. Video: `u32 codec id` (`h264`; 0 = disabled, 1 = config error), then 12-byte headers: a **session packet** (bit 63 set: u32 flags, u32 width, u32 height, new in v5, sent before each encoder (re)start, e.g. after RESET_VIDEO or rotation), or a frame header (u64 pts, bit 62 = config, bit 61 = key frame; u32 size). Touch events must carry the current video size from the session packet, or they are silently ignored. `cleanup=true` (default) deletes the jar at start, so we pass `cleanup=false` to keep the versioned jar in /data/local/tmp. `power_on=false` so a viewer never wakes the screen. GET_CLIPBOARD only answers with `clipboard_autosync=false`, and sends nothing while the clipboard is empty. The encoder emits frames only when the screen changes, so low fps on a static screen is normal. Encoders seen: redroid uses software (encoding runs in the media codec service, not in the app_process); the BitBrowser OPPO uses `c2.rk.avc.encoder`.
- **Fling velocity over remote links**: scrcpy-server stamps injected touches with the injection time, so moves that arrive in a clump get the same millisecond and Android computes an absurd fling. The adb server (no `delayed_ack`: host features lack it) keeps one write in flight per stream, so through the BitBrowser tunnel moves arrive in ~270 ms bursts; the relay through the phone's proxy clumps too. **Relay**: the browser sends each touch's event time (`t`), the hub turns it into the spacing to the previous touch (`dt`, same viewer only, ≤ 1 s) and, when both sides sent `X-Relay-Timed: 1` on the WebSocket handshake (older helper or API: raw bytes as before), frames control messages as `[u32 len][u16 dt, 0xFFFF = untimed][message]`; CpRelay writes each timed one at max(arrival, previous + dt) (never more than 1 s after arrival, never reordered); a DOWN waits ≤ 300 ms for the gesture's next message and is placed dt before it, so a DOWN that arrives a clump ahead of its moves doesn't become a long press. Android then sees the finger's real velocity: flicks fling and page (Reels needs it), drags that stop before release don't. **adb path** (no device-side process; also gestures without `t`): the hub holds the release until link RTT + 60 ms after the last move and sends one more stationary move first (Android's 40 ms "pointer stopped" rule drops the burst samples): drags stop where the finger stopped, but paging UIs only page after a drag past their distance threshold. Local devices are unchanged.
- scrcpy shows FLAG_SECURE windows black, just like STF (checked on Settings' PIN screen, `fl=… SECURE`). Only the `secure` source (CpCapture as uid 1000) shows them. Google's sign-in email step is not FLAG_SECURE on redroid 13.
- `jp.co.cyberagent.stf*` packages are STF's on-device agents and must never be uninstalled (`isProtectedPackage`).
- Google Workspace accounts may require a screen lock and device management (`DeviceManagementScreenlockRequired`); that is the organisation's policy, not a platform bug, and must not be bypassed.
